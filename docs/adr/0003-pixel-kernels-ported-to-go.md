# ADR-0003: 9 个 C 像素内核移植为 Go（黄金基准验收）

- 状态：已接受（2026-10-05，用户确认）
- 背景：原版算法真值是 9 个纯 C99 内核（`AdjustPixels.c` 1,157 行、`DitherPixels.c`、`HealPixels.c`、`WandPixels.c`、`ContentFill.c`、`LevelsPixels.c`、`BrushPixels.c`、`NoisePixels.c`、`LensPixels.c`，合计约 2,528 行）+ 原版 517 个逻辑测试。它们可在 Windows 原生编译。

## 决策

1. 内核逐个**移植为 Go 包**（`internal/pixel`），循环体用 goroutine 分块并行（按行带/瓦片），保持数值语义不变。
2. **黄金基准验收**：C 拷贝件 + 极小驱动在 Windows 原生编译出参考 PNG（参数 JSON 与 PNG 均入库）；Go 移植对同一参数逐像素比对，默认逐位一致，浮点敏感内核显式标注 ε（≤1/255）。
3. reference 区的 C 文件保持只读；harness 使用拷贝件（注明来源提交）。
4. 显示路径的逐像素实时操作（笔刷覆盖/特效/扭曲）不在 Go 内核范围——那部分归 WGSL（ADR-0004）；Go 内核负责导出真值、滤镜提交与 CPU 兜底。

## 理由

- cgo 复用 C 虽然零偏差，但 Windows 构建引入 mingw 矩阵、交叉编译与调试成本，长期维护差；内核是简单循环，Go 移植机械可验证，且并行化（分块 goroutine）在现代多核上收益直接。
- 517 个原版测试的语义 + 黄金 PNG 双重锚定，把"移植正确性"从人工评审变成机器断言。

## 备选与放弃原因

- cgo 直用 C：零偏差但构建矩阵重、调试链长、CI 慢；仅 HEIC/RAW/ONNX 等无纯 Go 替代的库保留 cgo。
- WGSL/WASM 承担全部逐像素：数值对齐最难、测试最难、导出路径仍需 CPU 实现。

## 后果

- 移植期需要纪律：每个内核一票、黄金基准先行、注释密度对齐原 C（数值常数与出处注释保留）。
- 大内核（Camera Raw ~1,157 行）按参数族拆票。
- Go 版可合法做原版没有的并行加速，但**输出必须与串行 C 一致**（浮点求和顺序差异需用定点/整数路径规避——原版内核本就以整数/查表为主）。
